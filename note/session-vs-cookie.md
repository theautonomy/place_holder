Strategy 1: The Default Identification Strategy (JSESSIONID)By default, Spring does not choose between sessions and cookies; it uses both via a hybrid architecture.Session Creation: When a user interacts with a Spring application, the underlying servlet container (like Tomcat or Jetty) creates an implementation of HttpSession on the server.The Identification Token: The server generates a unique, cryptographically random String called the Session ID.Cookie Transport Mechanism: The server responds with a Set-Cookie header containing JSESSIONID=<Session-ID>.Subsequent Identification: The browser automatically attaches this JSESSIONID cookie to every subsequent request. Spring looks up this token in its internal session registry to resolve the correct HttpSession and retrieve user attributes (such as the Spring Security SecurityContext).

In the Spring Framework, an HTTP session is primarily recognized and tracked using a unique Session ID extracted from incoming HTTP requests. This process depends on whether you are using the standard Servlet container implementation or the specialized Spring Session module.1. Standard Servlet Container MechanismBy default, Spring relies entirely on the underlying Servlet container (e.g., Apache Tomcat, Jetty) to manage and recognize sessions.The Cookie Method (JSESSIONID): When a client first connects, the server creates an HttpSession object and generates a unique token called the JSESSIONID. The container sends this ID back to the browser in a Set-Cookie header. On subsequent requests, the browser automatically sends the cookie back, and the container uses it to map the request to the correct in-memory session.URL Rewriting: If cookies are disabled in the client browser, the container falls back to identifying the session using a path parameter appended to the URL (e.g., /index.html;jsessionid=12345).
